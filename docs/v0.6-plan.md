## Open topics (raised 2026-11-08)

1. **Controlled access (strict ACLs).** Thomas wants Driftwood treated as a controlled class, with strict control over who can see and who can change its data. Today there are 5 roles, 24 ACLs and role checks inside the REST scripts; reads are all-or-nothing per table. To discuss: who may see secure hashes, Prod observations or update-set details; whether objects and observations need row- or field-level rules (by environment or category); who can import, collect, delete history and run fix scripts; separation between the collector account and people; and the audit of these actions. Output: an access model in the architecture design, then the ACLs.
2. **Architecture design document.** A full architectural design of Driftwood: context, components, data model, flows, security model, deployment, operations and roadmap. Started 2026-11-08 as a living document; it replaces the scattered design notes over time.

## Goal

Move Driftwood from "records per instance, compared on the fly" to "**one tracked object per thing, observed in every environment, with its drift status stored**".

Open *Table: incident* and you see each environment's definition and whether they agree. You can list "everything that differs on Prod" in a standard list view.

v0.6 is also the first version **installed and upgraded as an application version**, not by running scripts.

## 1. Tracked objects and observations

| Piece | What it is |
|---|---|
| **Tracked Object** (new plain table `tracked_object`) | One record per category + key across all instances, for example *Table: incident*, *Property: glide.authenticate.multifactor*, *Plugin: com.snc.incident*. Fields:<br>• category, key and name<br>• drift status (same · differs · missing somewhere · single instance)<br>• drift kinds (schema, config, clone, count, version, sys_id)<br>• present on N of M instances, differs on, missing on<br>• baseline instance, last compared<br>• parent object (a column's table) |
| **Observations** | Today's per-instance records (`tracked_item`, plus the plugin CIs until they move). They gain an **Object** reference. |
| **Writer** | Finds or creates the object the first time it sees a key, and sets the reference on insert. It stays change-only. |
| **Volume** | About 3,700 objects across today's 4 instances (plugins ~1,400, applications ~800, columns ~1,150, the rest small) |

Objects are plain records in v0.6. Applications, tables and plugins become CI classes in v0.7.

## 2. Stored drift

| Piece | What it does |
|---|---|
| **Drift engine** (new script include `ConfigNowDrift`) | Uses the same matching as the all-instances comparison: baseline ordering, ignore rules, version-only and count-only flags, optional sys_id. Writes the result onto each object. Change-only, so an object is updated only when its status, kinds or instance lists change. |
| **After every persist** | A collection or import recomputes only the objects it touched. |
| **Daily full pass** | New job *Driftwood - Recompute drift*, after the daily collection. Catches everything else, such as an instance's environment being changed. |
| **Prod drift** | List-only, as decided. No notifications or tasks yet. |

## 3. Plugins leave the CMDB

- **Fix script, dry run first:** copies every per-instance plugin record from `cmdb_ci_sn_tracked_plugin` to `tracked_item`, keeping first seen, last changed, history and links. It then switches the `plugins` routing to the plain table and deletes the plugin CIs (about 5,500 on dev466156).
- **Verification:** before and after counts, and a comparison run that must show no change in drift.
- **Not touched:** the plugin CI class itself stays until v0.7, when *SN Plugin* (one CI per plugin) replaces it.

## 5. Deployment, baked in (d38)

> **Amended 2026-11-08:** publishing to the application repository is disabled on personal developer instances ("Internal and Store uploading has been disabled"). The application repository stays the path for company instances. On PDIs, a release is installed with *Studio › Import from source control* from `main` or a release tag. Fix scripts don't run on their own after a Git import; on a fresh instance there is nothing for them to migrate. O07 is therefore: version 0.6.0 → PR `0.6.0` → `main` → tag `v0.6.0` → Git install on a clean PDI → Health and a first collection there.

| Need | How, from v0.6 |
|---|---|
| **Install and upgrade** | Driftwood is published from Git to the **application repository** and installed or upgraded through *My Company Applications*. Records, ACLs, roles, jobs and the 59 cross-scope privileges travel with the version. |
| **Data migrations** | **Fix scripts** in the app, each idempotent and dry-run-first: *Backfill tracked objects*, *Move plugins to plain records*, *Recompute all drift*. |
| **Health self-check** | New **Driftwood › Health** page and `GET /health`. Read-only, and checks:<br>• roles, tables, columns, ACLs and list layouts present<br>• jobs active, with their run-as user<br>• REST API active, old `/configurationnow` inactive<br>• cross-scope privileges against the expected 58 (missing or extra)<br>• retention settings<br>• last run status and age, object count, objects without observations<br>Also runs daily; failures are shown on the page and logged. |
| **Scripted installers** | Stay as developer tools: bootstrapping a PDI, retargeting a scope, building the version that gets published. The global-scope guard stays. |
